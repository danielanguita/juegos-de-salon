## D-595 · Críptico's answers never in plain text on GitHub
**Date:** 2026-11-20 · **Status:** current · **Relation:** — · **Topics:** anti-cheat
**Context:** The repo is public and the browser downloads `clues.js`. A player stuck on today's clue could
search GitHub and find its answer: in `clues.js`, in a PR or commit title («the owner's MANJAR clue»), a
branch or changelog file name, or the issue a player's proposed clue became. The owner asked that the
tickets and what they hold never give a clue away.
**Decision:** Each answer and its explanation live sealed in `clues.js` (`s`, `public/labs/cryptic/sealed.js`);
clues go in with `tools/generators/cryptic-clues.mjs add`, which seals them. Branches, commits, PRs, changelog
entries and docs say «one more clue», never the answer. A proposed clue's issue carries neither the clue nor
the answer; `feedback.mjs proposal <issue>` prints it from Firebase. `engine.test.mjs` fails on a plain clue
line in `clues.js` and on a bank answer in capitals in the pending changelog, the game's folder, its e2e
scripts or its docs.
**Why:** Searching is the easy way in, and the test catches the slip a session would make.
**Consequences:** It is a veil, not a lock: with no server the browser must know the answer, so a determined
player can still decode it. Answers already in git history (every clue added before this) stay readable
there; history is not rewritten. A proposal's discussion on GitHub talks about the clue without quoting it,
and better versions of it are worked out with the owner in a session.
