## D-596 · On the owner's own PR, the tick survives a later push that touches no 🔴 file
**Date:** 2026-11-20 · **Status:** current · **Relation:** amends D-575 · **Topics:** agents
**Context:** D-575 kept the tick only across "Update branch". Any other push asked again, so a PR the owner had approved came back for a second or third tap when its checks failed after the tick and a session pushed the fix, or when a rule that reached main meanwhile (D-594, the 25-word Labs card) made it change one line. The owner asked that their own PRs stop asking twice.
**Decision:** On an insider's PR (`INSIDERS`: the owner, the sessions, the repo's workflows), the `lane` job finds the latest commit the owner approved and the files the PR changed since then, net of main (head against a clean merge of that commit with main as merged in). If none is 🔴 (`lanes.json`), the tick carries: `owner-approval` turns green ("carried from …, D-596") and auto-merge goes on. A push that changes a 🔴 file again, a conflict that cannot be worked out, and every push to an outside PR (a fork, a contributor) ask again, as before.
**Why:** The owner's Yes is about the hard-to-reverse part of the PR. A later fix to a game, a text or a doc is the 🟡/🟢 work that never needs the owner anyway; asking again only cost taps. A new 🔴 change still gets its own look, and an outsider's push is never trusted on an old Yes.
**Consequences:** An owner's 🔴 PR asks once per change to a 🔴 file. `lanes.test.mjs` covers `carriesOwn`; docs/LANES.md says it.
