## C-12 · Tests

- Each game's engine has tests that run with node, without a browser. GitHub runs them all on each PR and each merge to main (D-143): a PR with ❌ is not merged. `main` requires `tests` and `end-to-end` (the summary of the scripts in Chrome), and a ready PR carries auto-merge: GitHub merges it on its own when both pass (D-216). The only exception is the owner explicitly saying not to auto-merge a PR (D-419).
- **A test watches it, not memory** (D-213): `node public/assets/js/games.test.mjs` requires of each game in `GAMES` its engine and its tests (C-2), the `window.__…` hook (C-14) and the spec with C-13's sections in order and the hook named. What a game does not yet meet goes in that test's `EXCEPCIONES`, with the decision that leaves it pending; when the game catches up, the test asks for the exception to be removed.
- Before publishing, the game is tested end to end in headless Chrome: a full game in each mode, with a reload mid-game and a rematch.
- Two-phone mode is tested with two browser instances, and at least once against the published URL.
- A change in a shared module requires repeating the regression of **every** game.
- Real screenshots of each screen are reviewed, not just the assertions' result: design problems are seen, not asserted. Remaking them is not reviewing them: before publishing, look at the contact sheet (`node tools/e2e/contact-sheet.mjs <seccion>`), which puts them together at the README's size (D-76).
- A screenshot is taken with the screen still. Frozen mid-animation, a list with staggered entries is photographed with rows at different widths and looks like a CSS bug that does not exist (D-76).
- A console without errors is part of the acceptance criteria.
- **Every screen is tested in every offered language** (D-199): each game's `languages.mjs`
  in `tools/e2e/` walks the screens of `paths.mjs` in each language of `LANGS` against
  Spanish. A script that checks something of one language walks `LANGS`, not a hand-written list, and
  takes what it expects from the dictionary: so a new language is tested the day it comes in.
- **Testing shortcuts go in the «T» tester tab** (D-551): playing one level or microgame directly, jumping to a state or simulating an end is a control registered with `setTesterContext` behind `labAccess`, never a button on the cover or a player screen, so the cover is always what players see.
- 🤖 **What is in the lab has a switch in the «T» tab; what left it has none** (D-567, the owner): every flag a page asks with `flag('<id>')` while it is 'lab' gets an on/off switch in the tester tab by itself (`labHere` in `flags.js`, `labSwitches` in `tester-ribbon.js`), on that phone only, so a feature is tried with and without it. A launched flag ('all') drops out of the tab on its own. A screen's own testing control (`setTesterContext`) for a lab feature is shown only while its flag is in the lab (`labHere.has('<id>')`), and the PR that removes the gate removes it.
